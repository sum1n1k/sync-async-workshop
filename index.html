Synchronous CPU work

The loop runs on the browser's main thread. It finishes before the next statement runs.

Keep these ideas separate
Sync / async describes how a result becomes available. Blocking / non-blocking describes whether the calling thread can continue. Sequential / concurrent describes how tasks are scheduled.

The busy loop is deliberately limited to 1.2 seconds and is only a teaching example. A timer does not perform the same CPU computation. The dot uses requestAnimationFrame, so it reflects main-thread responsiveness.

    Sequential await

    await pauses this async function.
    It does not block the main thread while the request is pending. Both examples are asynchronous.

    Promise.all waits for the promises passed to it. Calling the request functions starts the work. This is overlapping waiting, not evidence of parallel JavaScript execution.

    Use sequential requests when the next request needs the previous result, such as loading a profile before requesting that user's posts.

    This API deliberately delays responses. Real latency varies. Promise.all rejects if an input rejects; other requests are not automatically cancelled. This example waits for outstanding tasks to settle before allowing another run.

          The guard

          let latest = 0;

async function search(query) {
  const id = ++latest;
  const results = await request(query);
  if (id !== latest) return;
  render(results);
}

          The old request may still finish. The completed guard prevents it from changing the current UI. It does not cancel the request. Debounce reduces request frequency; it does not by itself guarantee response order.

          The fixed replay sends “java”, then “javascript” 150 ms later. The old “java” response arrives last. Reset invalidates earlier runs so late callbacks cannot repopulate the page.
